# Zindex authoring guide

How to write DSP scenes that render well. It is the reference behind https://zindex.ai/skill/SKILL.md. The machine-readable contract is the JSON Schema: https://zindex.ai/schemas/scene.schema.json and https://zindex.ai/schemas/ops.schema.json.

## Auto-layout: omit coordinates from nodes
DEFAULT TO AUTO-LAYOUT for nodes and edges. Set layoutStrategy at the scene-document root (alongside schemaVersion, scene, and elements - NOT nested inside scene.scene), and OMIT layout from nodes. Same convention for diagramFamily and palette - all three are document-root fields. Nested under scene.scene they are moved to the root before the scene is checked, and stored there; a field set in both places keeps the root's value. The layout engine positions nodes, routes edges, and places labels automatically.

  layoutStrategy: { direction: "LR" | "TB" | "BT" | "RL", nodeSpacing?: 30, rankSpacing?: 80 }

Canvas dimensions affect layout density: when scene.canvas is larger than the minimum required by node spacing, the planner auto-spreads nodes around their centroid to fill the available area (auto-spread only widens gaps). Bigger canvas = more breathing room; smaller canvas = tighter layout. Auto-spread never causes overflow. It happens when the engine lays out every node; after the first save a larger canvas set with updateScene adds room on the right and at the bottom, and autoLayout spreads the nodes into it.

Mixed mode: nodes WITH explicit layout are pinned. Nodes WITHOUT (or at exactly x 0, y 0) are placed next to their neighbors, around the pinned ones, which stay where they are until you ask for a new layout (below), unless a node that grows pushes them, a node a later edit adds needs more room for its edge label (below), a new task in a pool needs room in its lane or a column of its own, an edit moves one to another lane or a frame added or deleted round it would leave frames overlapping, or an `order` constraint an edit adds finds its two nodes the wrong way round.

Positions are kept: after the first save the engine records each node's position in its layout, and later edits keep it unless a node that grows needs the room, a node the edit adds needs more room for its edge label than the column it joins (that column and everything past it along the flow move just far enough), a task the edit adds to a lane needs the lane to grow or a column of its own (what lies past it moves), the edit moves a task to another lane (it is placed again there), an edit adds or deletes a frame round placed nodes and keeping them would leave frames overlapping or a frame holding a node that isn't its member, or an `order` constraint the edit adds finds its two nodes the wrong way round; then the engine places those nodes again, and the edit's changed lists them. New nodes are placed next to their neighbors; edges, labels and frames are redrawn each time; sequence diagrams follow message order, so their nodes stay at x 0, y 0; an edit puts a lifeline or message in its place with after or before (Operations, below). A node that grows (a longer label, more columns, resizeElement, or a layout smaller than its content needs) pushes the nodes in its way just far enough to keep the gap they had, at most the node spacing (the rank spacing along the flow), and a frame with its own layout grows where a member that grew or was pushed would cross its border, as a pool or lane always does. Sequence diagrams don't push. Coordinates you write are kept as written: a node you put on another one stays there, and NODE_OVERLAP_DETECTED names the fix. To make a placed node bigger where it stands, give resizeElement the side its flow enters: "left" in a left-to-right diagram, the direction when none is set, and "top" top to bottom or in an org chart, as in { "op": "resizeElement", "id": "decide", "size": { "width": 290, "height": 170 }, "anchor": "top" }. It keeps its center across the flow, so straight edges into it stay straight; without anchor it grows from its top-left corner, its center moves by half the growth, and an edge into a diamond's corner or a BPMN sequence flow can take a step. To lay out again, send autoLayout: { "op": "autoLayout" } lays out every node, as on a new diagram; { "op": "autoLayout", "elements": ["cache"] } places only the listed nodes again, around the others. A new layoutStrategy or diagramFamily set with updateScene lays out every node too, and so does removing one. These move nodes you positioned as well. In architecture, workflow, entity-relationship and UI flow diagrams and diagrams without a family, every frame but a pool, lane or fragment also drops its own layout and is laid out with its members. A frame that keeps its layout (a pool, lane or fragment, or any frame in an org chart or network) keeps its members where they are unless elements names them, and then they are placed again inside it. One that doesn't fit lands outside, and NODE_OUTSIDE_FRAME says so; a pool or lane grows to hold it instead.

ANTI-PATTERN: do NOT combine layoutStrategy with per-element layout.mode="absolute" coordinates on EVERY node. The two are contradictory at the all-elements level - layoutStrategy can only auto-position nodes that have no explicit coords. The most common failure mode is generating placeholder layout blocks like { mode: "absolute", x: 0, y: 0 } on every entity alongside a layoutStrategy declaration: x 0 and y 0 mean the node isn't placed yet, so the engine lays those nodes out and the blocks only add noise. The all-non-zero variant (every element pinned + layoutStrategy declared) pins every node, so the strategy places nothing. The clean pattern is: declare layoutStrategy at the document root, OMIT the layout block on every node you want auto-positioned, set explicit layout only on the specific nodes you want pinned. A diagram read back with view "dsp" has every position filled in: that is the engine's record of where it placed the nodes, so keep those blocks to keep the picture.

Frames (pools, lanes, containers) also auto-size from their children - omit layout from frames too. The engine computes frame bounds on every save, lays pools and lanes out round their members (see Swimlanes below), and lays out sequence fragments and activation bars from the messages they hold or name. Provide explicit layout only when you need pixel-precise control. A frame with its own layout keeps that box, growing only on a side a grown or pushed member would cross. Laying out a new diagram, the engine places nodes without regard to a fixed frame; a member added later goes inside it where there is room. NODE_OUTSIDE_FRAME reports a member outside. A pool's or lane's layout is only a minimum: they always grow to hold their members, so their members need no positions and never get NODE_OUTSIDE_FRAME. In org charts and networks, laying out every node can also make a fitted frame overlap another frame (FRAME_OVERLAP_DETECTED) or take in a node that isn't its member (NODE_IN_WRONG_FRAME); autoLayout with those nodes in elements places them again clear of the other frame. A frame with its own layout that is narrower than its title returns TEXT_OVERFLOW with the width it needs; widen it with resizeElement.

## Scene structure
{ schemaVersion: "0.1", scene: { id, canvas: { width, height } }, layoutStrategy?, elements: [...], styles?, constraints? }

Elements have a kind: "node" | "edge" | "frame" | "group" | "text" | "image" | "guide".

Nodes: { id, kind: "node", nodeType, shape?, label, layout?, textStyle?, icon? }
- nodeType: "service" | "database" | "objectStorage" | "queue" | "actor" | "generic" | "process" | "decision" | etc, plus family-specific types
- shape is OPTIONAL and defaults per nodeType. The normalizer fills the canonical glyph automatically: er.entity → rect, service → roundedRect, database → cylinder, objectStorage → bucket, workflow.start/end → ellipse, workflow.gateway* / workflow.decision → diamond, workflow.task / workflow.subprocess → roundedRect, er.attribute → ellipse, er.relationship → diamond, network.cloud → cloud, iconNode → iconBox, decision → diamond. Pass shape explicitly ONLY when you want a non-canonical glyph. Full enum: "rect" | "roundedRect" | "ellipse" | "diamond" | "cylinder" | "bucket" | "pill" | "hexagon" | "parallelogram" | "cloud" | "box3d" | "textBox" | "iconBox"
- layout is OPTIONAL: without it the engine places the node (layoutStrategy at the document root picks how)

**Storage convention.** Two storage classes, two shapes, as AWS, Azure and GCP reference architectures draw them:
- `nodeType: "database"` + `shape: "cylinder"` for row / key / document / search-indexed stores: Postgres, MySQL, Oracle, MongoDB, DynamoDB, Cassandra, Redis, Memcached, Elasticsearch, OpenSearch, InfluxDB, Timescale.
- `nodeType: "objectStorage"` + `shape: "bucket"` for blob-addressable storage: S3, GCS, Azure Blob, MinIO, R2, Backblaze B2.
Using cylinder for object storage (or bucket for a database) produces diagrams that look wrong to a human reviewer - the visual language is load-bearing semantic information, not decoration.

Edges: { id, kind: "edge", from: { elementId }, to: { elementId }, router?: "orthogonal" | "straight" | "curved", label?, edgeType? }
- Default to router "orthogonal" - the engine's router enters the side facing the source, at its center or straight across where the nodes line up, with obstacle-aware step-path fallbacks.
- "straight" is one line between the nodes' centers and "curved" one bowed arc, each ending on the nodes' outlines. Neither is routed round other nodes, and one that runs through a node gets the warning EDGE_CROSSES_NODE. Use "curved" for a loop back, which bows round the nodes between where it can, and "straight" only for a direct link with nothing between; not for a diagram's main flow.
- To pick where an edge meets a node, give the endpoint an anchor: from: { elementId, anchor: { side: "left", offset: 0.25 } }. side alone fixes the side; offset (0 to 1, from the side's top on left and right sides, its left on top and bottom ones) the place. Anchored edges never share a trunk, so anchors separate two edges that leave one side. Nodes don't move for anchors. A sequence message, a self-loop and an end with a column ignore their anchor (EDGE_ANCHOR_IGNORED). updateEdge replaces from and to whole: send the anchor again.

Long labels wrap on their own: a node's textStyle.wrap defaults to "auto", which keeps the label on one line up to 250 px (400 px for a diamond) and wraps a longer one there in even lines, the node growing taller; wrap: "none" keeps one line however long. Nodes saved before "auto" store "none": set "auto" with updateNode to wrap them. Multi-line text at a width you choose: set textStyle: { wrap: "word", align?, verticalAlign? } on a node with a layout width and layout.autoSize: "content"; the node keeps the width and the engine gives it the height the wrapped text and its icon need, growing down from its top edge; nodes it grows into move down to keep the spacing (the node spacing in a left-to-right flow, the rank spacing in a top-to-bottom one). The grown height isn't stored: it follows the text. wrap: "character" also breaks long identifiers and URLs. Without autoSize the node keeps its layout height, and TEXT_OVERFLOW gives the height text needs that doesn't fit. Or break lines with \n and let the engine size the node. Don't use node + text overlay workarounds.

## When to reach for which element kind
Before declaring "Zindex can't do X", check this list. Most "limitations" are actually unfamiliar primitives:

- **Standalone text label** (titles, captions, callouts, legends, descriptive paragraphs OUTSIDE a node): use `{ kind: "text", text: "Section heading", layout: { mode: "absolute", x, y, width, height } }` in a scene, or `createText` (the same fields) in an edit. Text elements support `textStyle.wrap: "word"` for line-wrapped paragraphs and accept \n for explicit line breaks.
- **Bullet lists in text**: just put unicode bullets in the text content, e.g. `text: "Features:\n• Fast\n• Reliable\n• Cheap"`. Combine with `textStyle: { wrap: "word" }` to wrap long bullets.
- **Horizontal or vertical separator line spanning the canvas**: use `{ kind: "guide", orientation: "horizontal" | "vertical", position: 250 }`. Guides always render as dashed full-width/height lines - perfect for dividing a diagram into sections.
- **Dashed line on an edge or shape stroke**: set `style: { dash: [4, 4] }` (or any number array). Works on edges (`{ ..., style: { dash: [4, 4], stroke: "#cc0000" } }` for a red dashed arrow) and on element strokes.
- **Custom fill/stroke colors**: inline `style: { fill: "#cccccc", stroke: "#cc0000", strokeWidth: 2 }` works on every element kind. Or define a named token in scene.styles.
- **Image embed** (logos, screenshots): use `{ kind: "image", assetRef: "...", layout, fit? }`, its file a `data:` URI in the scene's `assets`. In an edit, `updateScene` with `assets`, then `createImage`.
- **Hide without deleting**: `visible: false`. The element keeps its space but isn't drawn, nor any edge at it; a hidden frame hides only its box and title.
- **Grouping for selection / movement only** (no visible container): use `{ kind: "group", children: [...] }`. For a visible bordered container, use `{ kind: "frame", containerType: "generic", children: [...] }`.

If your design needs something not covered here, prefer composing it from the above primitives over concluding the platform can't do it.

## Operations

Send these in `ops` on `diagram_edit` (or `POST /v1/diagrams/{id}/revisions`). The full shapes are in https://zindex.ai/schemas/ops.schema.json and https://zindex.ai/docs/reference/operations/.
createNode, updateNode, deleteElement, createEdge, updateEdge, moveElement, resizeElement, setStyle, setText (accepts textStyle), groupElements, ungroupElements, createFrame, createText, createImage, addConstraint, removeConstraint, autoLayout, updateScene, restoreRevision.

In a sequence diagram a new lifeline is added on the right and a new message or note at the bottom. To put one between two others, give createNode or createEdge `after` or `before`: the ID of the element it goes next to (a lifeline beside a lifeline or actor, a message or note beside a message, a note or a fragment, joining that message's fragment). updateNode and updateEdge take the same to move one. The element named must exist when the op runs (ORDER_TARGET_NOT_FOUND); other elements refuse both (ORDER_NOT_SUPPORTED). To add a message after a fragment rather than as its last row, name the fragment. The outline lists messages and notes in drawn order. A fragment is laid out with its rows (its layout is ignored), and each operand starts at a row (operands[].startsAt), so its divider moves with it; a row placed `before` an operand's first row becomes its first. Deleting or moving an operand's first row starts it at its next (FRAGMENT_OPERAND_REMOVED when none is left). `{ "op": "createEdge", "id": "m_cache_get", "edgeType": "sequence.message", "from": { "elementId": "checkout" }, "to": { "elementId": "cache" }, "label": "GET cart", "after": "m_verify_ok" }`

An edit with an error saves nothing and returns `VALIDATION_FAILED` with `errors`. That includes an op on something it can't change, such as `moveElement` on an edge or `resizeElement` on a node the engine hasn't placed yet. Fix what each error names and resend with the same `baseRevision`. Within one edit, an op may name an element a later op creates, except the element `after` or `before` names and the frame a createNode or updateNode `frame` names, which must exist when the op runs.

updateScene modifies scene-level metadata on an existing scene without recreating it - use it to change title, brief, palette, styles, assets, layoutStrategy, diagramFamily, or canvas: `{ "op": "updateScene", "title": "New Title", "palette": { "nodeFill": "#003366" } }`. A new layoutStrategy or diagramFamily lays out every node again, as autoLayout without elements does. Pass null for brief, palette, layoutStrategy or diagramFamily to remove them, or for an entry of assets; removing layoutStrategy or diagramFamily also lays out every node again.

autoLayout has the engine place nodes again and keeps the new positions: `{ "op": "autoLayout" }` lays out every node, as on a new diagram; with `"elements"` (node IDs only) it places just those nodes again, clear of the others. It doesn't move nodes with a relative layout or sequence diagrams. Without `"elements"`, in architecture, workflow, entity-relationship and UI flow diagrams and diagrams without a family, every frame but a pool, lane or fragment drops its own layout and is laid out with its members; members of a frame that keeps its layout stay where they are; named, they are placed again inside the frame, and one that doesn't fit lands outside (NODE_OUTSIDE_FRAME), except in a pool or lane, which grows to hold it.

restoreRevision makes the next revision equal to an earlier one and must be the only op in its edit: `{ "op": "restoreRevision", "revision": 3 }`. `diagram_edit` also takes it directly as `restoreRevision`.

## Diagram families
ALWAYS declare diagramFamily at the scene-document root on every scene you create (alongside schemaVersion, scene, elements - NOT nested inside scene.scene). The field is technically optional in the schema, but it is effectively load-bearing: it gates family-specific behavior the engine and downstream tooling rely on (sequence-family exemption from same-label fan-in collapse, ER-family auto-promote-fk-labels and column anchoring, workflow-family BPMN conventions, family-namespaced node types, etc.). Omitting it forces the engine into the generic-flowchart base case and leaves downstream tooling unable to segment by diagram type. Nothing warns you when it's absent, so declare it every time. Allowed values: architecture, workflow, entityRelationship, sequence, network, orgchart, uiflow.

For parallel processing paths, perimeter actors, or process logic with decisions, prefer workflow + pool/lane over architecture + generic frames - splitting work into swimlanes renders cleaner than fanning edges out of one oversized central node.

- architecture: service / database / queue / storage / externalSystem nodes (service for gateways, database for caches). Default LR auto-layout. **For architecture diagrams without explicit frames, set autoGroup: "byNodeType" in the document's top-level extensions to emit subtle background bands grouping nodes by their nodeType ("Services", "Databases", "External Systems", etc.)** - lifts the diagram from a flat blob of boxes into a scanable layered architecture. Architecture-family only; skipped silently for other families. Skipped when (a) the scene already has user-authored frames containing the candidate nodes (no double-wrap), (b) every node shares a single nodeType (single band is pointless chrome), or (c) the nodes of one type are scattered (a node of another type sits between two of them in a column). The response doesn't say when banding was skipped.
- workflow: Full BPMN. workflow.start / end for basic, messageStart / messageEnd for message-triggered. intermediateTimer / Message / Error for catch events, intermediateThrowMessage for throw. terminate ends entire process. subprocess renders with [+] marker. 4 gateways: gateway (exclusive), gatewayParallel, gatewayInclusive, gatewayEvent. For decision diamonds without a BPMN-spec marker (x, +, circle, pentagon) use workflow.decision - its label renders INSIDE the diamond per the broader flowchart convention; the four gateway types use the BPMN-spec external-label convention. **For sequence flows between workflow steps, set edgeType: "workflow.sequenceFlow"** - it gets the BPMN-spec triangle arrowheads. workflow.messageFlow gets open circle / open arrow for cross-pool messages. Generic edges (no edgeType) default to a target-end triangle arrowhead too, in a scene or from createEdge - direction is the dominant semantic in every diagram family, so the engine arrows by default; opt out with `endpoints: { endArrow: "none" }` for the rare undirected case. A type's own arrowheads aren't stored, so changing an edge's edgeType with updateEdge changes them; view "dsp" shows only the arrowheads you set (an older version can still list its type's; they draw the same). **For state-transition / conditional-flow edge labels, use the UML / SCXML / BPMN convention `EVENT [guard] / action`** - the renderer splits the segments into typographically-distinct tspans automatically (event 12px standard, guard `[...]` 10px muted, action `/ ...` 10px muted italic), so the eye locks onto the event name first. Detection is content-based (any label containing balanced `[...]` OR a ` / ` separator); plain labels render unchanged.
- entityRelationship: er.entity / er.weakEntity nodes. Relationship lines (er.relationship, er.identifying) draw solid; add style.dash [6, 4] for a non-identifying one. Set extensions.columns: [{ name, type?, pk?, fk?, unique?, nullable?, comment? }] on an er.entity for compartmented rendering with PK/FK badges. (The shape { name, type, key: "PK"|"FK", unique?, nullable? } is also accepted and normalized to the canonical form; a column that is both needs pk and fk.) **To add / remove / modify columns on an existing er.entity, use updateNode with the FULL replacement extensions.columns array - the array is replaced wholesale, not merged. There is NO addColumn / removeColumn / updateColumn op; the valid ops are listed under "Operations" above.** Crow's-foot cardinality glyphs are auto-inferred from column metadata: the only PK column → "one", one of several PK columns → "many"; an FK column, including one that is also pk, → "many" by default, narrowing to "one" (unique, or the entity's only PK column), "zero-or-many" (nullable), or "zero-or-one" (both). So a join table keyed by its FKs is many-to-one with each parent when each of its edges names its column (endpoint.column, or a label matching the column), and a table whose PK is also its FK is one-to-one; such a column shows both badges. To override, set cardinality on the endpoint: "one" | "many" | "zero-or-one" | "zero-or-many" | "one-or-many" - author-set values are always preserved. Inferred values aren't saved: every save infers them again, so they follow later column changes, and view dsp shows only what you wrote. To anchor an edge at a specific column row inside an entity, as database diagram tools draw it, set endpoint.column to the column name; when only the FK side has the column name, the engine falls back to the target's sole PK row automatically so most FK edges need only label="<fk_column>" or column on the source side. Such a label anchors the edge and isn't drawn; set style.forceLabel: true to draw it too, still anchored at the column. Self-FK loops (parent_id-style) draw a U-bracket between the FK row and the PK row inside the same entity. Entity rects auto-grow to fit the longest column row + header + rows; explicit layout.width/height are treated as a minimum, so you don't need to hand-tune dimensions to avoid column overflow. LR auto-layout works well.
- sequence: sequence.actor / sequence.lifeline for participants - the sequence resolver auto-positions lifelines and orders messages by their position in the elements array (definition order = visual order). Lifeline headers auto-size to fit their labels (declared 100 px width is a floor, not a cap). Each lifeline renders a head bar at the top AND a matching foot bar at the bottom by default (the UML convention) - do NOT author duplicate node shapes for the bottom row, the platform draws them. Set showLifelineFeet: false in the document's top-level extensions (not scene.extensions) to suppress foot bars. 5 edge types: sequence.message (sync, filled arrow), sequence.async (open arrow), sequence.reply (dashed open arrow), sequence.create (dashed filled arrow), sequence.destroy (filled arrow + X terminator). For activation bars, add a sequence.activation node with extensions.startsAt (the message that starts it; the bar is on the lifeline it arrives at) and extensions.endsAt (the message that ends it), and no layout. For combined fragments, use a frame with containerType "fragment", the messages and notes it holds as children, extensions.operator ("alt" | "opt" | "loop" | "par" and so on), and the title for the first operand's guard, with its brackets ("[charge succeeded]"); for each further operand add extensions.operands: [{ startsAt: "<message or note id>", guard: "else" }], guard without brackets (they are added), which draws a divider above that row. Leave layout out of fragments: the engine lays them out with their rows. Fragments nest or follow each other: list each row in one fragment. For UML notes / annotations between messages (e.g. "Postgres crashes"), use sequence.note with extensions.anchor: "<id>" where <id> is a sequence.lifeline OR sequence.actor in the scene - the note centers "over" that participant (the UML 2.5 §17.4 convention). For notes that span multiple lifelines, use extensions.anchor: ["<idA>", "<idB>", ...] - the note's bounding box spans from the leftmost to the rightmost named lifeline, also centered-over semantics. Notes interleave vertically with messages by their position in the elements array - in a scene, place the note element BETWEEN the two messages it should appear between; in an edit, createNode with `after` naming the message it follows (or the fragment, to go below it). Notes render as a rounded rect with a folded top-right corner (UML convention).
- network: network.server / router / switch / firewall / cloud / client nodes. Force-directed layout (no inherent direction).
- orgchart: org.person / org.role with label "Name\nTitle". Add accentColor for department stripe. org.directReport (solid) / org.dottedLine (dashed) edges. Auto-layout is a tidy tree, top to bottom; it doesn't read layoutStrategy.
- uiflow: uiflow.screen / modal with label "Title\nDescription" (first line title bar, rest body). uiflow.entry / exit for start/end circles. uiflow.navigate / back (dashed) / action edges.

Swimlanes (workflow): a pool is a frame with containerType "pool" whose children are lane frames (containerType "lane"), in the order they stack; each lane's children are its tasks, events and gateways. Leave layout off the pool, the lanes and their nodes: the engine lays them out as BPMN tools do (in org charts and networks it only keeps each node inside its lane; columns aren't shared). Lanes run along the flow and stack across it; every node a lane lists is placed inside it; each lane is as deep as its contents need (at least 60 px, or its title's length plus 16 px); columns are shared across lanes and pools, so the flow reads as time. laneDirection "vertical" stacks the lanes top to bottom (BPMN's horizontal pool) and the flow runs left to right; "horizontal" puts them side by side (a vertical pool) and the flow runs top to bottom. When layoutStrategy.direction runs along the lanes' stacking, laneDirection wins. Several pools stack across the flow in document order, 40 px apart; a pool with no nodes (a black-box participant for message flows) is drawn at its least depth. createFrame needs at least one child, so write a pool with no nodes in the scene sent to diagram_create. A pool's layout is a minimum anchored at its corner. To add a task to a lane later, createNode with frame set to the lane's ID: it takes a free place in its column inside the lane, or the lane grows and what lies past it moves across the flow; a task between two placed columns opens a column. updateNode with frame moves a task to another lane, where the engine places it again. No op adds a lane to a saved pool or reorders its lanes (frame moves nodes only): in one edit, deleteElement the pool, which leaves its lanes and tasks in place, and createFrame it again with the same id, title and laneDirection and its lanes in children in their new order. Edges with an end at the pool itself go with it, so create them again in that edit. createFrame needs at least one child, so create a new lane with its first task in children. Lanes are pushed, never pulled back, so send autoLayout afterwards for a compact picture. Lanes along the flow (phases), and reordering lanes or pools to reduce crossings, aren't supported; a frame inside a lane (a subprocess) is fitted round its members, not laid out with them. Nodes a pool lists beside its lanes go in an untitled band after them (POOL_NODE_OUTSIDE_LANE).

## Refining auto-layout results
Use align constraints (addConstraint with type "align") to align nodes within containers on a shared axis. Use order constraints to control spatial relationships between nodes (e.g. source leftOf target). When the engine places the children of a generic frame, it also aligns them on the layout axis, centering the group so nodes appear professionally aligned without manual intervention.

## Hard ordering constraints
Use type: "order" constraints to control node placement when the engine lays out every node. Example: { type: "order", source: "db", target: "api", relation: "rightOf" } ensures the database is placed to the right of the API. Relations: leftOf, rightOf, above, below, sameRank. On a saved diagram, adding an order constraint places its two nodes again, in order, when they aren't already in that order; every other node keeps its position. Conflicting constraints are gracefully dropped.

## Styles
The `style` field on every element accepts EITHER a named-style string OR an inline style object - both forms validate.

Inline (put directly on the element): `style: { fill, stroke, strokeWidth, dash, textColor, fontFamily, fontSize, cornerRadius, opacity, accentColor }`. `dash` takes a number array like [4,4] for dashed strokes.
Named (define once in scene.styles, reference by key): `styles: { brand: { fill: "#003366" } }` then `style: "brand"` on each element.

Text color auto-adjusts for contrast against custom fills if you don't set textColor explicitly. Set textColor to override; an edge label, or a label drawn outside its shape (BPMN events and gateways), is still made lighter or darker if it would be unreadable on what it lands on.

Scene-level palette: set `palette` at the scene root (e.g. `palette: { nodeFill: "#003366", edgeStroke: "#004488" }`) to override theme defaults for all unstyled elements - element explicit styles still win.

Pick colors for a light canvas. A dark preview (`POST /v1/diagrams/preview` with `theme` set to `dark`, `blueprint` or `sketch`, or the playground's theme menu) adapts them, keeping each hue; a dark `palette.background`, or a dark `canvas.background` with none, makes the scene a dark design, drawn as written. MCP's `diagram_render` takes no theme: it draws as saved versions are drawn, in the default style (or `dark` for a dark `canvas.background`), with the scene's colors as written.

## Icons
Set icon to a semantic key. ~102 built-in icons across two packs:
- Lucide (~52): "lucide:database", "lucide:server", "lucide:cloud", "lucide:shield", etc. Match the node's text color.
- AWS (~50): "aws:lambda", "aws:s3", "aws:ec2", "aws:dynamodb", "aws:api-gateway", "aws:certificate-manager", "aws:backup", "aws:budgets", etc. Use brand colors.

URL fallback: "icon": "https://example.com/custom.svg" is drawn with the URL as its href, loaded by whoever views the SVG, and left out of PNG output. Built-in icons embed as base64, so the image needs no other request.

AWS icons (aws:*) render icon-only by default - no bounding rectangle - so they composite cleanly over container fills (VPC, subnet, region). Only the aws and lucide packs exist (every key: https://zindex.ai/docs/reference/element-types/#icons). An unknown key, such as gcp:*, azure:* or a Lucide name outside the built-in set, renders no icon (a gcp:* or azure:* node keeps its box) and the save returns ICON_NOT_FOUND with the keys spelled like it, so use a URL for anything else; icon: null on updateNode removes an icon. For cloud architecture diagrams, place icon nodes inside a frame with a tinted fill and the icons appear on the colored background, matching AWS Architecture Icons convention.

DO NOT emit defensive 'fill: "#ffffff"' on cloud-icon nodes - the platform treats explicit "#ffffff" / "#fff" / "white" / "rgba(255, 255, 255, *)" as default-equivalent and applies the icon-only override anyway, since a white knockout under an AWS icon is essentially never the deliberate choice. To opt into a bounded look, set style.fill to a non-white color ("#ffeeaa", "#dde9fb", "#fefefe") or to "transparent" / "none" for a bordered transparent-fill icon.

The same default-equivalent rule applies to module/group frames inside colored containers, BUT only for binary endpoint values: a frame with fill="#ffffff" or "rgba(255, 255, 255, 1)" inside a colored ancestor (VPC, subnet, region) is overridden to "none" so the ancestor color shows through. Translucent values are PRESERVED - that's the AWS-reference card-on-subnet aesthetic.

For module/group frames inside colored containers, the recommended alpha is rgba(255, 255, 255, 0.5). This produces a visible-but-subtle white card that lets the parent's color show through clearly, matching AWS-reference contrast. Higher alphas (0.7-0.85) look mostly opaque and obscure the parent color; lower alphas (0.2-0.3) lose the card grouping. 0.5 is the sweet spot. Use no fill (or "none") if you want fully transparent dashed boundaries with no card effect.

EDGES TO A GROUP AS A WHOLE. Edges may target a frame ID directly (not just nodes). The arrow then terminates at the frame's border, on the side facing the source, straight across where the source lines up and otherwise at the side's center. Use this when the connection is semantically abstract - "this thing depends on Regional Services" or "uses the Customer Managed Resources cluster" - rather than a specific service inside. AWS Reference Architecture diagrams draw it the same way: a sidebar group gets one arrow to the group, not one to each service inside.

Two cases for using a frame as the target:

1. Fan-out consolidation. When a source has multiple edges to siblings of a single parent frame and the connection is "this thing connects to the pool as a whole," prefer ONE edge to the parent frame.
   - Consolidate: one edge efs_shared -> file_systems. NOT three edges efs_shared -> fsx_ontap / efs_customer / fsx_lustre.
   - Keep individual: three edges internet_gateway -> alb / nat_gateway / nlb (each load balancer serves different traffic).

2. Abstract group dependency. When a single edge represents "this thing uses the X grouping" without specifying which member, target the frame directly.
   - web_application -> regional_services (the cluster as a whole). NOT web_application -> s3_regional (a specific service that happens to live inside it).
   - api_proxy_lambda -> regional_services. NOT api_proxy_lambda -> dynamodb.

Why it matters for both cases: an edge whose target is inside a frame routes through the frame's border to reach the specific node, which visually reads as "the arrow trails off into the frame interior" - especially when the inner node is a borderless cloud-provider icon. Targeting the frame keeps the arrow tip on the frame's clean dashed border, matching reference-quality cloud architecture diagrams.
